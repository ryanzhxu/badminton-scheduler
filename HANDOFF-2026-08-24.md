## 1. What the app is

A **Badminton Rotation Scheduler**. It builds fair rotation schedules for a
weekly Wednesday badminton session, then publishes a shareable QR code and link.

Real users, real weekly use. The group plays Wednesdays. A Cloudflare Cron
Trigger pulls that week's sign-ups from cal.com at roughly noon Pacific on
Wednesday, generates the rotation, and publishes it automatically. Players open
one durable link to see it.

Core behaviors:

- Fair sit-out rotation — sit-out counts stay within one round of each other.
- 2v2 doubles, with 1v1 singles for overflow.
- Partner and opponent variety — repeat pairings are penalized, back-to-back
  rematches penalized harder.
- Conflict groups — selected players must never be **teammates**. They may still
  face each other as opponents.
- Six languages, dark mode, live sync across viewers, a cross-session
  leaderboard, and a check-in tab for late arrivals.

## 3. Architecture

### The three-copies rule — the single most important constraint

The scheduling algorithm exists in **three** places and they must stay
byte-identical in behavior:

1. `index.html` — the SPA's inline `<script>`.
2. `worker/src/index.js` — the Cloudflare Worker. **This is the live production API.**
3. `server.js` — the Express server. Dead in production, but load-bearing for tests.

`npm test` runs every scheduling test against all three, plus an explicit
identical-seed equality check. If you change the algorithm in one copy and not
the others, the suite fails. This is deliberate: it enforces alignment
mechanically instead of by memory.

`server.js` cannot be deleted. Render serves it as plain text and never executes
it, so it is dead code in production — but `tests/helpers/load-scheduler.js`
reads it as the third algorithm copy.

### Layers in `index.html`

One self-contained file: HTML structure, CSS with custom properties for the
teal/green palette, and the full app script in a single bare `<script>` tag.
No build step. No frontend dependencies.

Tabs: **Setup**, **Schedule**, **Check-in**, **Leaderboard**.

### Backend split

`worker/src/index.js` has features `server.js` does not: the cal.com auto-import,
the player registry, the schedule index, and the leaderboard. This is a known,
documented gap. If `server.js` is ever brought back into production use, that
logic needs porting.

### The five hardcoded contracts

From `REFACTOR.md`. A refactor breaks the two halves apart only if it touches one
of these:

1. **Render publish path.** `publishPath` is `"./"`, so the repo root is served
   verbatim. `index.html` must stay at the root, as one file, in a bare
   `<script>` tag.
2. **Frontend to backend URL.** `API_BASE` in `index.html` hardcodes the Worker
   URL. Renaming `name` in `worker/wrangler.toml` changes the `workers.dev`
   subdomain and breaks every call.
3. **Backend to frontend URL.** `PROD_SHARE_BASE_URL` in `worker/src/index.js`
   hardcodes the Render URL. Only the Wednesday cron uses it, because a cron has
   no browser origin to read. If it goes stale, generated QR codes point at a
   dead host, nothing errors, and it surfaces a week later at the court.
4. **The API surface.** Eleven routes, called from eight sites in `index.html`.
   No build step and no type checker, so a rename fails only at runtime.
5. **Version alignment.** `APP_VERSION`, `package.json`, and
   `worker/package.json` must be bumped together and must always match.

What a refactor **cannot** break: CORS is `Access-Control-Allow-Origin: *` on
every response including preflight, so the frontend origin is free to move.
Share links use a query parameter, not a path, so Render needs no SPA rewrite
rules and there is no `_redirects` file to keep in sync.

## 5. The scheduling algorithm — current design

**A major rewrite landed in `cdf6ca3`.** Anything you remember, or read in an old
comment, about a stochastic random-restart search is stale.

### Removed and gone

`assignCourts`, `makeTeams`, `MAKE_TEAMS_ATTEMPTS`, and the old standalone
`repeatCost` no longer exist. `MAKE_TEAMS_ATTEMPTS` was `600` — a fixed literal
present since the project's first commit, never benchmarked against anything, and
only rationalized after the fact. Do not reintroduce it.

`usedTeams` as a name is also gone. The old binary "has this exact team been used
before" Set was replaced by a counting pair history.

### Current functions

**[verified 2026-08-24]** These are the 16 declarations in `REQUIRED_NAMES` in
`tests/helpers/load-scheduler.js`. Extraction is by name, so renaming any of
them breaks the suite in all three copies at once:

```
REPEAT_PARTNER_WEIGHT, REPEAT_OPPONENT_WEIGHT, CONSECUTIVE_OPPONENT_WEIGHT,
shuffle, teamKey, conflictPair, teamOk, pairKey, createPairHistory,

```

it was retired; that was wrong.

Each must stay in the form `function X(` or `const ... X =`.
`extractDeclaration` matches only those two shapes. Converting one to a `let`
arrow, a class method, or an object property breaks extraction everywhere.

### How it works

**`getLayout(n, nc)`** — given `n` players and `nc` courts, computes the court
breakdown: doubles at 4 players, singles at 2, plus subs. Greedy search over
substitution counts from 0 up, preferring full doubles and minimal singles.
Example: 13 players on 3 courts gives 3 doubles plus 1 sub.

**`greedyMatch(items, costFn)`** — generic greedy minimum-cost perfect matching
over an even-length list. Builds every candidate pair, shuffles first so
equal-cost ties vary run to run, stable-sorts by cost ascending, then greedily
accepts the cheapest pair whose both items are still free. Not guaranteed optimal
— true optimality needs a blossom algorithm — but effective for these small
costs, and it runs once instead of hundreds of random restarts.

**`matchPartnersRespectingConflicts(activePl, hist, conflictGroup)`** — the
single conflict group behaves as one "no two of these may be teammates" clique.
This matches clique members to non-clique partners **first**, while non-clique
supply is still plentiful. That ordering is what guarantees zero conflict
violations whenever a valid pairing exists. A plain unconstrained greedy pass can
paint itself into a corner and force an avoidable violation purely from bad
candidate-order luck. A violation is only possible when the clique is larger than
half the active doubles pool (`k > n/2`), which is genuinely infeasible to avoid,
not an algorithm bug. It degrades gracefully rather than crashing.

**`buildRoundCourts(activePl, layout, hist, conflictGroup)`** — splits the
shuffled active pool into singles slots and a doubles pool. Runs
`matchPartnersRespectingConflicts` on the doubles pool to form partner pairs.
Then runs `greedyMatch` again on those pairs, with cost equal to the summed
cross-pair opponent-repeat cost, to decide which pairs face each other. Runs
`greedyMatch` separately on the singles pool, with cost equal to opponent-repeat
cost directly, since singles has no partners and no conflict restriction.

**Pair history** — `createPairHistory()` returns
`{ partners: Map, opponents: Map, lastOpponents: Set }`. It is derived state,
never persisted in the schedule JSON, and is rebuilt by replaying rounds via
`rebuildSchedulingState()` in the SPA and the extend handlers in both backends.

**Cost weights** **[verified 2026-08-24]**, `index.html`:

```js
const REPEAT_PARTNER_WEIGHT=1, REPEAT_OPPONENT_WEIGHT=0.6, CONSECUTIVE_OPPONENT_WEIGHT=3;
const BASE_ROUNDS=15, EXTEND_ROUNDS=5;
```

Cost is **squared** in the number of prior meetings: `n² × weight`. **Squaring is
load-bearing, not incidental.** The old binary check stopped discriminating once
every combination had been used once. Do not "simplify" it back to a binary
check. Facing the same opponent in the immediately preceding round costs an extra
flat `CONSECUTIVE_OPPONENT_WEIGHT`, because a back-to-back streak is what players
actually notice and report.

**Fair sit-out rotation** — before each round, sort shuffled players by current
sit-out count, extract the bottom `layout.subs` as this round's subs, increment
their counts. Variance stays within 1.

### Measured results

- After the rewrite, max partner repeats dropped to 3 across 30 seeds on the
  12-player reference scenario. The test tolerance is 5. **[from transcript]**
- The bug that started all of this: two players faced each other 5 to 11
  consecutive rounds. After the fix, always 1. Total meetings out of 15 dropped
  from 9–13 to 2–4, against a theoretical fair floor of about 2.7 for 12 players
  over 15 rounds. **[from transcript]**

### No skill-based balancing

An earlier skill-tier feature — rate players Beginner/Intermediate/Advanced,
balance court totals — was built and then **removed**. See the user's explicit
ruling in section 7. Do not reintroduce a skill field without re-adding the

## 6. Feature inventory — what exists today

### Setup tab

Court count input, defaulting to `3` as a real value, not a placeholder. Player
management: add, bulk import, demo injection. Conflict picker. Generate button.

Input processing: `parseRawName()` strips email addresses and role suffixes such
as `- Organizer`. `computeDisplayNames(list)` auto-abbreviates to first name, or
first plus last initial when there is a collision, so "John Doe" and "John Smith"
render as "John D." and "John S.".

### Schedule tab

Round navigation, court grid with 1 to 3 columns depending on court count,
sit-out banner, QR share card, and a collapsed-by-default constraint validation
panel with a `#val-badge` status indicator that reads "All good" in green or
"N issues" in amber even while collapsed.

`renderSessionSummary()` shows player count, court format, and round count in a
strip below the round navigator. `renderLastUpdated()` shows a "Last updated"
line sourced from `schedule.updatedAt` or `generatedAt`, for every loaded
schedule.

Manual round editing: an edit/lock toggle per round. Players can only be moved
while edit is enabled. `toggleEditRound()` and `handleSwapClick()` implement
tap-to-swap between team slots, then call `rebuildSchedulingState()`.

The per-player stats table was **removed** from this page. Player stats live only
on the Leaderboard now.

### Check-in tab

Per-player attendance status: Not arrived, Playing, Left. An "Everyone's here"
bulk button. `regenerateUpcomingRounds()` recomputes only rounds from
`currentRound` onward, so past rounds are preserved.

One **global** "Edit names" toggle, not one per player. All chips become inputs
at once. Clicking outside or pressing Enter saves every change at once; invalid
or duplicate entries revert individually rather than blocking the whole save.
Escape cancels. Functions: `toggleCheckinEditMode()`,
`handleCheckinOutsideClick()`.

An always-visible "+ Add player" row (`addCheckinPlayer()`) calls
`regenerateUpcomingRounds()` to reflow the layout for the new headcount. This is
the only way to add a late arrival on a shared link, because Setup is hidden
there.

Renaming internally uses `renamePlayer()` and `rebuildSchedulingState()` to
propagate through `rawPlayers`, `attendance`, `conflictGroup`, `demoPlayers`,
`sitC`, and every schedule round past and future, then rebuilds `pairHistory` and
`sitC` from a full replay.

### Leaderboard tab

`loadLeaderboard()` fetches `GET /api/leaderboard`. Aggregates per canonical
player: `games`, `sits`, `sessions` (distinct schedules appeared in, whether they
played or sat out), `uniquePartners`, `uniqueOpponents`.

**The "Played" column is a per-player total across all sessions, not a
head-to-head count.** This confused the user once — two players both showing 150
games meant they were the two most consistent attendees at 15 of 15 sessions, not
that they played each other 150 times. There is no pairwise "games against each
other" feature anywhere in the app. Expect this question again.

Player identity: `normalizePlayerKey()` trims, lowercases, and collapses
whitespace. `canonicalPlayerName()` checks `players:aliases` first, then falls
back to the registry's first-seen spelling. **First-seen spelling wins** as the
canonical display name. `registerPlayers()` runs on every schedule generation,
so the registry stays current with no separate sync step.

### Shared views

Loading `?scheduleCode=...` sets `isSharedView` and calls
`applySharedViewMode()`. This hides the Setup tab button and the "← Setup"
shortcut, but **keeps "New rotation" visible**. Viewers land on the Schedule tab.
`isSharedView` reverts if the load fails.

### Live sync

Viewers on the same share code hold an SSE connection to
`GET /api/schedule/:code/stream`. Pushed snapshots re-apply through
`applyScheduleSnapshot()`. Each viewer stays on their own current round index
rather than jumping to the end. `currentScheduleRevision` guards against applying
stale snapshots. `qrSyncToken` increments on each `syncShareQr()` call so old
responses are discarded if a new sync starts.

### The durable "current" link

`?scheduleCode=current` is a stable, reusable link that always shows whichever
schedule is presently active. Before Wednesday noon it shows last week's; once
the cal.com auto-import publishes a new one, the same link reflects it, with no
new QR or link to reshare.

Backend: `GET /api/schedule/current` special-cases the literal string `current`
as a pseudo-code in `handleGetSchedule`, resolving via `loadCurrentSchedule()`
against the `current_schedule` KV pointer. SSE streaming is **not** supported for
the literal `current` pseudo-code, because there is no single Durable Object room
for a moving target; `handleScheduleStream` returns 400 for it.

Frontend: `isCurrentLinkMode` displays a stable `?scheduleCode=current` link and
QR via `applyCurrentLinkShareDisplay()`, and polls `GET /api/schedule/current`
every `CURRENT_LINK_POLL_MS` (45000 ms) via `pollCurrentSchedule()`. If the
underlying `code` changes, it re-applies the snapshot from round 0 and reconnects
SSE to the new code. If only the revision changed, it preserves the viewer's
current round. Regular per-code links keep their original SSE-only behavior.

### cal.com auto-import — Worker only

Cron `0 20 * * 3` runs `scheduled()`, which calls `runCalAutoImport(env)`:

1. `resolveCalEventTypeId()` resolves and KV-caches the cal.com event type ID for
   `CAL_USERNAME`/`CAL_EVENT_SLUG` via `GET /v2/event-types`.
2. `fetchCalAttendeeNames()` paginates `GET /v2/bookings` for that event type
   within the current Pacific-calendar-day window (`pacificDateWindow`,
   DST-aware), flattening and deduping attendee names through the same
   name-cleanup logic as manual bulk import.
3. Builds layout and rounds with the existing `getLayout`/`generateRounds`, fixed
   at `AUTO_IMPORT_NUM_COURTS = 3` and `AUTO_IMPORT_ROUND_COUNT = 15`, generates
   a QR/share code, and marks it as the active schedule — the same effect as a
   human clicking Generate then Share.
4. Idempotent per Pacific calendar day via `cal:last_pull_date`, so retries and
   duplicate cron firings are safe.

Manual trigger: `POST /api/cal/run-import?token=<CAL_API_KEY>`. Supports
`&dryRun=true` (no writes, no side effects, just previews the pull) and
`&date=YYYY-MM-DD` (override the target Pacific session date to test a future or
past date without affecting the real cron's idempotency).

Cron Triggers are fixed UTC, so the actual Pacific local time drifts by an hour
across the two DST transitions each year. This is accepted, not a bug — the
idempotency key makes an off-by-an-hour firing safe.

There is **no proactive notification** when the auto-import runs. This is
deliberate; see section 8. Observability is a `console.log`/`console.error` line
visible via `wrangler tail` or the Cloudflare dashboard Logs tab, plus the
durable link always reflecting the latest schedule.

### Versioning

the header title as "Internal Tools · v1.7.2". There is no build step, so it is
not read from `package.json` at runtime. Bump `APP_VERSION`, `package.json`, and

Semantic versioning: patch for fixes and small tweaks, minor for new user-facing
features, major for a breaking change to the schedule data shape or a public API
endpoint.

## 10. Operational playbook

### Commands

```bash
npm test                 # 20 tests, all three algorithm copies, ~0.5s
npm run check            # node --check on server.js and worker/src/index.js
npm start                # run server.js locally on port 5000 (`npm run dev` is an alias)
node --check worker/src/index.js
cd worker && npm run check
python3 -m http.server 8000   # UI only, does not exercise the API
```

`npm test` is the regression suite for rotation fairness and it checks all three
copies stay aligned. **Any change to the scheduling algorithm must pass it, and
the change must be applied to all three copies.**

For frontend-only edits, `npm run check` plus a browser check of the changed
behavior is enough. `npm test` is not required when no scheduling logic is
touched.

### Verification rules

- Changed the algorithm? `npm test` must pass, in all three copies.
- Changed `server.js`? `node -c server.js` plus a local run.
- Changed `worker/src/index.js`? `node --check worker/src/index.js` before deploy.
- Changed JSON persistence? Verify the saved file still loads with the existing
  schema.
- Frontend only? Quick browser check.

### Test harness notes

`tests/helpers/load-scheduler.js` lifts the scheduling functions out of each
source and runs them in a `node:vm` sandbox with a seeded mulberry32 PRNG. It
extracts rather than imports, because `index.html` is intentionally a
self-contained single file with no build step, and importing the backends would
pull in express or hono and start a listener.

Sandbox globals are declared with `var` on purpose — inside a vm context only
`var` bindings become properties of the context object, which is how tests inject
state. Output is JSON round-tripped before `deepStrictEqual`, because objects
created inside a vm carry that context's prototypes and would otherwise compare
unequal despite being structurally identical.

Failures carry the seed and the offending numbers, so they are reproducible.

If you change the scoring weights, expect to re-measure. Thresholds are set from
observed behavior with margin, wide enough to distinguish real regressions from
seed noise.

A prior session verified the suite was load-bearing by temporarily zeroing the
new penalty weights in the Worker copy only, and confirming specific failures:

```
seed 1: the two Advanced players faced each other for 7 consecutive rounds (limit 3)
seed 1: a pair met 10 times (limit 6)
seed 1: after extending, some pair faced each other for 7 consecutive rounds (limit 4)
worker/src/index.js (Cloudflare Worker) diverged from index.html (SPA) on seed 1
```

Do that again if you materially change the cost model. A test suite you have not
seen fail is not yet a guardrail.

### Testing against production is dangerous

**Every schedule generation writes a permanent KV entry, updates the durable
`current` pointer, and feeds the leaderboard index.** This has polluted real
user-facing data twice.

Before any live testing:

- Use `dryRun=true` where it exists (`POST /api/cal/run-import`).
- Prefer a local `server.js` instance.
- If you must generate against production, plan the cleanup, and **snapshot KV
  to a local file first**. Deleted KV data cannot be recovered.

### KV cleanup, if you ever need it

History: about 96 dev/test schedules were deleted once, keeping 5 real Wednesdays
(7/8, 7/15, 7/22, 7/29, 8/5). Then 16 more test schedules from a smoke-testing
burst were deleted, and 14 players' `lastSeen` dates were reverted. Then 12 fake
demo names and schedule `BADM-6LXE` were removed, leaving 24 real names across 15
sessions.

Rules learned the hard way:

- **Always check whether a schedule is the `current` one before deleting it.**
  Deleting the active schedule breaks the `?scheduleCode=current` durable link.
- Classify real versus test by Pacific calendar date. Real sessions are
  Wednesdays. The user's rule: for dates with more than one schedule, keep only
  the last one; for non-Wednesdays, drop them.
- Sequential `wrangler kv get` is too slow past a few dozen keys. Use the
  Cloudflare REST API with bulk fetch.

### Windows and PowerShell gotchas

These come from the prior machine. **If the new machine is macOS or Linux, most
do not apply — but the BOM and encoding lessons about KV data still do.**

- PowerShell does not support `&&`. Use `;` to chain.
- PowerShell has no heredoc. For git commit messages, write to a temp file and
  use `git commit -F <file>`.
- **PowerShell `>` redirection produces UTF-16LE with a BOM,** which breaks
  `JSON.parse` in Node. A stray BOM written into a KV value once silently broke
  `/api/schedule/current` and looked like a stale-data bug. Use
  `Out-File -Encoding utf8`, or write via Node's `child_process` directly.
- **Piping a secret corrupts it.** `$value | wrangler secret put NAME` appends a
  trailing newline into the stored secret. Write to a temp file and use
  `cmd /c "wrangler secret put NAME < file"`, or type it interactively.
- A failed command mid-chain does not stop later commands unless
  `-ErrorAction Stop` is set. This caused one accidental file deletion.
- Windows CRLF line endings broke a regex during scripted text surgery. Account
  for `\r\n` explicitly; do not assume `\n`.

### Editing the i18n dictionaries

Each language dictionary is minified onto a single very long line. Manual
find-and-replace on those lines is error-prone — one prior attempt introduced an
extra closing brace. The established technique is a **disposable Node script
using regex** to do the bulk edit across all language blocks, verify the result,
then delete the script. Account for CRLF.

### Git conventions

Commit messages in this repo are short, imperative summaries. Match that. Do not
write verbose multi-paragraph messages, with the exception of genuinely
architectural commits like `546dbf2`.

Parallel feature work uses `git worktree` with one branch per feature, so
multiple agents can work without file collisions. Worktrees prevent collisions
during editing, not at merge time — merges still need hand resolution, usually in
the single-line-per-language i18n dictionaries.

## 12. Tribal knowledge, in one list

- The algorithm lives in three places. The test suite is the only thing keeping
  them aligned.
- Squared repeat cost is load-bearing. A binary check stops discriminating once
  every pairing has been used once, which is exactly the bug that started the
  rewrite.
- The clique-first ordering, not the greedy matching itself, is what guarantees
  zero conflict violations.
- `MAKE_TEAMS_ATTEMPTS = 600` was never benchmarked. It is gone. If anyone asks
  why 600, the answer is "no reason."

  are expected. People keep signing up. Pulling the final list at run time is
  intentional.

  one: the pointer was only updated on explicit Share or auto-import, not plain
